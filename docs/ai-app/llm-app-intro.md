---

## 一、大模型应用是什么

日常聊天的对话窗口只是大模型最基础的形态。**大模型应用**指的是把模型当作一个"推理引擎"嵌入到产品里，让它围绕具体业务干活：客服问答、知识库检索、代码助手、数据分析、自动化流程等。

一个典型的分层视角：

| 层次 | 内容 | 例子 |
|---|---|---|
| 模型层 | 预训练/微调好的大模型本身 | GPT、Claude、GLM、Qwen、DeepSeek |
| 编排层 | 把模型、数据、工具组织起来的应用逻辑 | LangChain、LlamaIndex、自研编排代码 |
| 应用层 | 面向用户的最终产品 | 智能客服、知识库问答、编码助手 |

多数开发者要做的是**编排层和应用层**——模型调用只是其中一步，更多工作量在数据、流程和交互上。

## 二、Prompt 工程：最便宜也最有效的优化

Prompt（提示词）是与模型沟通的文本输入。同一个模型，写法和效果可能天差地别。几个经过验证的基本手法：

### 1. 给模型"角色 + 任务 + 约束"

```text
你是一名资深后端工程师。请审查以下 Go 代码，只指出安全与并发问题，
按严重程度排序输出，不要重写整个文件。
```

### 2. 少样本示例（Few-shot）

与其描述格式，不如直接给 1~3 个输入/输出示例，模型会模仿示例的风格与结构。

### 3. 思维链（Chain of Thought）

对推理类任务，让模型"先分步分析再给结论"，通常显著提升准确率。对支持推理模式的模型，也可以直接开启其内置的深度思考能力。

### 4. 结构化输出

需要程序消费模型结果时，明确要求 JSON 并给出字段定义，必要时在代码侧做 schema 校验与重试，不要假设模型输出永远合法。

> **实践建议**：Prompt 要进版本管理、要做回归测试集。业务一变就手改提示词，是应用质量失控最常见的原因。

## 三、RAG：让模型"开卷考试"

### 为什么需要 RAG

模型的知识停留在训练数据截止日，也不知道你的私有文档。**RAG（Retrieval-Augmented Generation，检索增强生成）**的思路是：先从知识库里检索相关内容，把检索结果塞进 Prompt，再让模型基于这些材料回答——相当于让模型开卷考试。

### 基本流程

```text
离线索引：文档 → 切分(Chunking) → 向量化(Embedding) → 存入向量库
在线问答：用户提问 → 向量化 → 相似度检索(可加重排) → 拼装 Prompt → 模型生成
```

### 关键环节与常见坑

- **切分**：按语义边界切（标题、段落），块太小丢上下文，太大稀释重点。常见 300~800 字 + 10%~20% 重叠。
- **Embedding 模型**：中文场景选择对中文友好的 Embedding 模型，它决定了"找得找得回"。
- **检索质量 > 生成质量**：检索不出来，模型再强也答不对。可叠加关键词检索（BM25）做混合检索，再用重排（Rerank）模型精排。
- **引用溯源**：让回答标注出处，既方便用户核查，也便于定位检索问题。

RAG 与微调的取舍：知识频繁更新、需要溯源的场景优先 RAG；固定领域且要求特定风格/格式的场景才考虑微调，且微调不能替代 RAG 提供实时知识。

## 四、Function Calling 与 Agent：让模型"动手"

### Function Calling

现代模型 API 支持声明一组工具（函数名、参数 schema、描述），模型判断需要时返回"我想调用某个函数及参数"，由你的代码真正执行后把结果回传，模型再继续。模型负责**决策**，代码负责**执行**——边界要分清。

### Agent 的最小闭环

Agent 本质上是把 Function Calling 放进一个循环：

```text
while 未完成:
    模型思考 → 选择工具并给出参数 → 代码执行工具 → 结果回传给模型
```

在这个循环上再加记忆（历史对话、中间产物）、规划（任务拆解）与反思（失败重试），就构成了目前主流的 Agent 形态（ReAct 模式是其经典代表）。

### 工程上的现实约束

- **循环要有上限**：限制最大步数与 token 预算，防止死循环烧钱。
- **工具设计要克制**：每个工具职责单一、描述清晰，工具太多会显著降低选择准确率。
- **危险操作加确认**：写库、发请求、删文件等副作用动作，务必在代码层加审批或沙箱。

## 五、技术选型速览

| 决策点 | 选项 | 适用 |
|---|---|---|
| 模型来源 | 云端 API | 快速起步、能力强、按量付费 |
| | 本地开源模型（vLLM/Ollama 部署） | 数据敏感、成本可控、可定制 |
| 编排框架 | LangChain / LlamaIndex | 生态全、原型快 |
| | 直接调 API + 自研编排 | 流程简单、需要完全掌控 |
| 向量库 | Milvus、Qdrant、pgvector | 从轻量到生产各有梯度 |

**建议**：框架不是必需品。RAG 的核心是检索质量，Agent 的核心是任务拆解与工具设计，这些理解比"用了什么框架"重要得多；简单场景直接调 API 往往更清晰、更好调试。

## 六、评估：应用能否上线的分水岭

大模型应用"演示惊艳、上线翻车"的分水岭通常在评估体系：

1. **建评测集**：从真实用户问题中抽样，覆盖典型与边界场景；
2. **自动化指标**：检索命中率（Recall@K）、答案相关性、结构化输出的合规率；
3. **LLM as Judge**：用强模型按评分标准给回答打分，人工抽检校准；
4. **线上监控**：记录每次调用的 Prompt/检索结果/输出与用户反馈，持续迭代。

## 七、学习路线建议

1. 先把官方 API 文档过一遍，亲手完成"对话、流式输出、Function Calling"三个最小示例；
2. 手写一个不依赖框架的迷你 RAG（几百行即可），打通"切分 → 向量化 → 检索 → 生成"全链路；
3. 在 RAG 之上加工具调用循环，实现一个能查资料 + 执行命令的小 Agent；
4. 给自己的应用建评测集，体会"改一版 Prompt → 跑一遍评测"的工作流；
5. 再回头按需引入框架与开源方案，理解它们分别替你做了什么。
