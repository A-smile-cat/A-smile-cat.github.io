# X（Twitter）科技新闻自动检索 → AI 分析 → 公众号推文：方案调研报告

> 调研日期：2026-09-09  
> 目标：给定一个近期科技新闻/技术圈事件，AI 能自动检索 X 上的帖子和评论，汇总分析后产出公众号推文，并附上 X 原文链接（方便截图）。



---

## 一、需求拆解

整条链路分四步：

1. **检索**：按事件关键词搜索 X 上的高热帖（原帖）和评论（回复）
2. **汇总**：去重、按热度/代表性筛选、保留作者名和推文链接
3. **分析**：AI 归纳社区观点分歧、技术细节、情绪倾向
4. **产出**：中文公众号推文 + 逐条 `https://x.com/用户名/status/ID` 引用链接清单（供截图）

---

| -------------------------------------- | ----------------------------- | -------------------------------------------- | --- | ------------------- | ------------------------------------------------------------------------ |

补充：Nitter/XCancel 这类免登录镜像前端 2026 年 8 月刚被 X Corp 发律师函勒令关停（9 月初部分恢复），随时可能再死，**不适合作为依赖**，最多当兜底。

### 补充说明：Nitter/XCancel 属于哪一类通道？

Nitter/XCancel 不属于上述五条通道中的任何一条，严格说是第六类：**镜像代理前端（mirror/proxy frontend）**。

**它本质上是"别人帮你爬"**：

- Nitter/XCancel 自己不存数据，其服务器在后台用**运营者自己准备的 X 账号会话池**实时抓取 x.com，再把结果渲染成轻量 HTML 页面给访问者
- 技术上它与通道④⑤（爬虫）同源——都是模拟登录会话绕过官方 API，只是账号不是用户出的，而是镜像站运营者出的；用户访问的只是一个"二手网页"
- 这也是它 2026 年 8 月被 X Corp 律师函打击的直接原因：X 认定其"非法使用 API、抓取数据、动用登录会话"

**与五条通道的对比**：

| 维度       | Nitter/XCancel    | 其他通道                           |
| -------- | ----------------- | ------------------------------ |
| 要不要 X 账号 | 不要                | 官方 API/爬虫要，Grok API/第三方 API 不要 |
| 要不要付费    | 不要                | 官方 API 贵、第三方按量、Grok 按调用        |
| 数据接口形态   | 网页 + RSS，无结构化 API | 全是结构化 API 或 SDK                |
| 自动化友好度   | 差（HTML 解析脆弱、限流频繁） | 好                              |
| 稳定性      | 极差（律师函、实例随时关停）    | 相对可控                           |

**对本用途的结论**：只能当**人工兜底**——某条推文链接打不开时，把域名换成 `xcancel.com`（路径不变）快速看一眼内容。不适合接进自动化流水线，原因：① 无结构化返回，需写脆弱的 HTML 解析；② 实例存活率不稳定，今天能用不代表下周能用；③ RSS 功能在多数实例上已残废。

### 关键结论

- **最省事、最合规**：xAI Grok API 的 `x_search`。一次调用约 $0.005，一个事件检索 10 次也就 5 美分，返回结果自带推文链接。缺点是要能付费（海外卡）。
- **最省钱、可控性最强**：twikit / agent-twitter-client + 自己的 X 账号。免费，能精确控制搜索语法（`min_faves:100 lang:en since:2026-09-01`）、能拉某条推文下的全部回复。
- **两者混合**也常见：用爬虫库抓数据，用任意 LLM 做分析写作，不必用 Grok 写稿。

## 三、关于"我提供账号和密码，需要吗？"

**需要账号，但建议不要直接发密码，分两种给法：**

### 给法 A（推荐）：只给 Cookie，不给密码

1. 你在自己电脑浏览器上正常登录 x.com
2. F12 → Application（应用）→ Cookies → `https://x.com`
3. 复制两个关键值：
   - `auth_token`（登录凭证，有效期很长）
   - `ct0`（CSRF 令牌，配合用）
4. 把这两个字符串发给 AI / 写进本地配置文件

优点：

- 密码不经过任何对话或第三方
- 爬虫库和 Playwright 都支持直接用 Cookie 免登录（twikit 的 `load_cookies()`、agent-twitter-client 的 cookie 缓存、tweet-harvest 的 `auth_token` 注入）
- **重要**：twikit 文档明确警告"反复调用 login 是封号高危行为"，首次登录后必须保存 Cookie 复用，之后不再碰密码

### 给法 B：给账号密码

只有首次生成 Cookie 时才需要。流程是本地脚本登录一次 → `save_cookies('cookies.json')` → 之后全部走 Cookie。如果账号开了两步验证（2FA），twikit 也支持 TOTP。

### 风险提示（必须知道）

- 用爬虫库访问 X 违反其服务条款，**理论上存在限流（搜索 50 次/15 分钟）和封号风险**
- 建议：**用一个小号跑**，不要用主力账号；控制频率（单次任务几十条足够，远低于限流线）；发布/点赞等写操作完全不用碰
- Cookie 属于敏感凭证，只写在本地配置文件，不要提交到 git

## 四、推荐落地方案（WorkBuddy Skill/Agent 流水线）

### 方案一：零账号方案（Grok API）

```
用户给出事件关键词
  → Skill 调 xAI API（Responses API + x_search 工具，搜索近 7 天 X 讨论）
  → 拿回帖子列表（作者、内容、链接、互动数）
  → 主模型（任意 LLM）汇总分析 → 按公众号模板写推文
  → 输出：推文.md + 引用链接清单.md
```

配置成本：一个 xAI API Key + 海外支付方式。代码量最小，一天能跑通。

### 方案二：自有账号方案（twikit，推荐长期用）

```
首次：账号登录一次 → 保存 cookies.json（此后不再用密码）
用户给出事件关键词
  → Python 脚本调 twikit：
     ① search_tweet('关键词 lang:en min_faves:50', 'Top')  → 高热原帖 20-50 条
     ② 对选中的核心帖子 get_tweet_by_id → 拉取热评回复
     ③ 输出 JSON：{作者, 昵称, 内容, 点赞/转发数, x.com 链接}
  → AI 分析 JSON → 写公众号推文（含"X 网友怎么看"观点碰撞段落）
  → 附引用链接清单，每条可直接打开截图
```

- 依赖：`pip install twikit`（需代理环境访问 x.com，设 `HTTPS_PROXY`）
- 频控：搜索 50 次/15 分钟，单次任务只用 3-5 次搜索，绰绰有余
- 参考 twikit 仓库 `ratelimits.md` 和 `ToProtectYourAccount.md`

### 方案三：第三方 API 方案（不想碰账号、又不想用 Grok）

- twitterapi.io：注册拿 API Key（送 $0.1 试用金），REST 直接调，$0.15/千条
- 已有现成开源 MCP Server：`@kaitoinfra/twitterapi-io-mcp-server`（12 个只读工具：搜帖、拉回复、拉引用转推、趋势等），可直接配进 AI 客户端，让 AI 用自然语言搜 X

## 五、产出物模板（每次任务输出两个文件）

1. **公众号推文.md**：标题 + 事件概述 + 技术要点 + "X 社区反应"（正反观点各 2-3 条，注明用户名）+ 结语
2. **参考链接.md**：表格列出每条引用的 `x.com/用户/status/ID` 原链接、作者、核心观点、互动数，逐条打开即可截图

## 六、建议的下一步

1. 确定通道：如果愿意付费省事 → 方案一；愿意提供小号 Cookie → 方案二（性价比最高）
2. 若选方案二：在浏览器登录 X 后把 `auth_token` + `ct0` 两个 Cookie 值给我（或写入本地配置），我来搭脚本和 Skill
3. 拿一个具体事件（比如最近某次模型发布）做端到端试跑，验证检索质量和推文格式后再固化成 Skill
